Getting Started with Git

Install, configure, and collaborate with a repository

Part 1: Install Git

Git is a version control tool that records changes to files over time. GitHub is a website that can host Git repositories and support collaboration. Installing Git on your computer gives you the command-line tool; it does not automatically create or connect a GitHub account.

NoteStart here

Install Git from git-scm.com/downloads. On Windows, Git for Windows includes Git Bash. On macOS, install with the installer or, if Homebrew is installed, run brew install git. On Linux, use your distribution’s package manager (for example, sudo apt install git on Debian or Ubuntu).

Open a terminal (for example, the Terminal tab in Positron) and check that Git is available:

git --version

If a version number appears, Git is installed and ready to configure.

Part 2: Configure Git

These settings identify you on commits. Use the name and email you want associated with your work. If you use GitHub, the email should be one associated with your account; GitHub also provides a private no-reply email if you prefer not to expose your address.

Set your name:

git config --global user.name "Your Name"

Set your email address:

git config --global user.email "you@example.com"

Use main as the default branch name for newly created repositories:

git config --global init.defaultBranch main

Check the saved settings:

git config --global --list

Part 3: Start or get a repository

Option A: Clone a repository that already exists

Copy the repository URL from GitHub (or another Git host), then run:

git clone https://github.com/OWNER/REPOSITORY.git
cd REPOSITORY

Replace OWNER/REPOSITORY with the actual account and repository name. Cloning downloads the repository and sets up a remote, usually named origin.

Option B: Start a local project and connect it to an empty remote

In the terminal, move into the project folder first (cd path/to/project), then initialize it:

git init -b main

Stage and commit the current files (see the next section), create an empty repository on GitHub, and connect it. Do not initialize the GitHub repository with a README or license if the local folder already has its own commit; starting with an empty remote avoids unrelated-history errors.

git remote add origin https://github.com/OWNER/REPOSITORY.git
git remote -v

Part 4: Save changes with commits

A typical cycle is inspect → stage → commit. A commit is a named snapshot of staged changes; it is saved locally until pushed to a remote.

See which files changed:

git status

Stage selected files (recommended when you want to review exactly what goes into the commit):

git add path/to/file

Or stage all current changes in the project:

git add .

Review what is staged:

git diff --staged

Create a commit with a short, informative message:

git commit -m "Add initial project files"

Writing useful commit messages

Write the message as a concise description of what the change does. Start with a verb when practical, such as Add, Fix, Update, or Remove. For example: Fix sample ID parsing or Add installation instructions. Keep unrelated work in separate commits. The message describes the change; it is not a place for passwords, tokens, or private information. these messages are visible to anyone looking at your repository, so keep them professional and accurate.

Part 5: Pull and push

A pull brings remote work into your current branch. A push sends your local commits to the remote. Before starting work with collaborators, pull the latest changes. If Git reports a conflict, it needs a human decision about how to combine the edits; resolve the marked files, then stage and commit the resolution.

For a branch that already tracks its remote counterpart, the usual commands are:

git pull
git push

Your first push: name the branch and set its upstream

For a new local branch, use -u (same as --set-upstream) and name both the remote and branch:

git push -u origin main

Here origin is the remote name and main is the local branch being pushed. The -u option records the upstream connection, so later git pull and git push can usually omit those names. If the branch is named something else, replace main with that branch name. To see the current branch, run git branch --show-current.

ImportantWhen the remote already has a commit

If a repository was created on GitHub with a README, license, or other commit while your local repository has separate history, the first push may be rejected. The safe path is usually to clone that GitHub repository and add your project files to the clone. If you need to combine existing histories, pull and resolve the situation deliberately; do not force-push as a first fix, because that can overwrite other people’s work.

NoteOne simple habit

Before committing, run git status and review the staged changes. Commit a focused set of changes with a clear message, then push when the work is ready to share.
